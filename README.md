# grounding-verifier

An n8n workflow that checks whether a claim generated by an LLM says more than the quote it rests on.

## The problem

Verifying model output usually comes down to one question: is the quote in the source? That is not enough - a quote can be faithful and the claim can still reach beyond it.

A case found while building the pipeline:

- `quote`: gold prices have risen much faster than mining costs during the [...]
- `claim`: Gold prices have risen much faster than mining costs.

The RSS snippet ends at that point, so the model received a sentence with no ending. The quote matches the source word for word, but it breaks off in the middle of a qualifier; the model ignored the break and produced an unconditional claim. The case did not arrive from the feed on its own - the quote was substituted manually at the extractor's input. Failures do not show up on demand, so waiting for one is not a test. The quote verifier is checked in both directions: a tampered quote has to return `false`, and the original with an extra space has to return `true`.

## How it works

```
Schedule Trigger → RSS Read → Limit → extractor (LLM) → Code1 → quote verifier (Code2) → Filter → judge (LLM) → Code3 
```

| Component | Role |
|---|---|
| Extractor | marks claims in the text along with the verbatim quotes that support them |
| Code1 | splits the `claims` list into separate items with explicit index mapping and re-attaches metadata |
| Quote verifier (Code2) | deterministic check of whether the quote occurs in the source |
| Filter | drops items whose outcome is already known |
| Judge | a single question: does the claim stay within the scope of the quote |
| Code3 | assembles the status from three independent sources |

The judge receives only `claim` and `quote`. It never sees the article.

## Statuses

For every claim the pipeline returns exactly one of four disjoint statuses:

| Status | Meaning |
|---|---|
| `no_claims_stated` | the article contained no claims - a valid empty result, not a failure |
| `quote_not_found` | the quote does not occur in the source |
| `claim_out_of_scope` | the quote is genuine, the claim is broader than it |
| `verified` | the claim stays within the scope of the quote |

## Design decisions

### Quote verification without the model

Checking that a quote is present is done deterministically - here, a string comparison - rather than by an LLM, following the rule that the model only does what cannot be done deterministically. This is what makes the two reasons for rejection distinguishable (`quote_not_found` and `claim_out_of_scope` as separate statuses). Had a single LLM judged both, the only available information would be that something did not pass.

### Judge and extractor on different models

The judge runs on a different model than the extractor, because a model is a poor judge of its own output - it tends to approve what it produced itself. This is an architectural requirement, not a preference.

Here the separation is only partial: the extractor runs on Gemini Flash 3.6, the judge on Flash 3.5. The "different model" condition is met, but versions within one family share an architecture and part of their training data, so they may share blind spots - separating across providers would be stronger. Forced by the lack of a free API tier for Gemini Pro.

### Judge without access to the article

The judge receives only `claim` and `quote`, because more context here is an information leak. Its task is to check whether the claim says more than the quote alone supports. With the full text it would start checking whether the claim agrees with the article - an easier question, and the wrong one. Given the full text, the case above would pass as `verified`, because the claim does agree with the article; it is the quote it does not fit.

## Limitations

- **The source is interchangeable.** `etftrends.com/feed` was chosen because ETF Stream publishes no RSS feed; switching sources means one field in one node.
- **Three items per run.** The LLM runs once per item; in grounding verification what matters is the depth of analysis of a single article, not throughput.

## Running it

```bash
docker run -d --name n8n -p 5678:5678 \
  -v n8n_data:/home/node/.n8n \
  --restart unless-stopped \
  docker.n8n.io/n8nio/n8n
```

Import `grounding-verifier.json` through the workflow menu → Import from File. Requires your own Google Gemini API key configured as a credential in both LLM nodes.
